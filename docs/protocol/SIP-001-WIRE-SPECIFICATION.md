# SIP-001: Sovra Wire Protocol Specification (Version 1.0.0)

**Standard:** SIP-001 (Sovra Improvement Proposal 001)  
**Layer:** Wire & Transport (TCP / WebSocket / WebRTC-Direct / BLE)  
**Status:** Living Standard / Authoritative  
**Date:** 2026-11-18  
**Author:** Sovra Core Protocol Team  
**Compatibility:** Bitcoin BIP-like Wire Standard / BitTorrent BEP-like Framing  

---

## 1. Abstract

This specification defines the universal byte-level wire protocol for the **Sovra Autonomous Mesh Network**. Any independent client implemented in **Rust, Go, C++, Python, or Swift** can establish peering, exchange encrypted signaling, synchronize distributed social CRDT state, and participate in BitSwap storage swarms by conforming to the packet framing, serialization, and cryptographic verification rules defined in this document.

---

## 2. Universal Packet Framing

All frames exchanged between Sovra nodes over TCP streams, WebSocket binary messages, WebRTC DataChannels, or BLE packets MUST adhere to the following 75-byte minimum canonical binary frame:

```
+-------------------+-------------------+-------------------+-------------------+
|  Magic (4 Bytes)  | Version (1 Byte)  | MsgType (2 Bytes) | Length (4 Bytes)  |
|    0x534F5652     |       0x01        |    Big-Endian     |    Big-Endian     |
+-------------------+-------------------+-------------------+-------------------+
|                                                                               |
|                             Payload (N Bytes)                                 |
|                       RFC 8785 Canonical Serialization                        |
|                                                                               |
+-------------------------------------------------------------------------------+
|                                                                               |
|                        Ed25519 Signature (64 Bytes)                           |
|                      RFC 8032 Signature over Frame Header + Payload            |
|                                                                               |
+-------------------------------------------------------------------------------+
```

### 2.1 Field Specification

| Field Offset | Field Name | Size | Type | Description |
|---|---|---|---|---|
| `0x00` | `Magic` | 4 Bytes | ASCII | Constant `0x53 0x4F 0x56 0x52` (`'SOVR'`). Packets lacking this magic header MUST be dropped immediately without processing. |
| `0x04` | `Version` | 1 Byte | UInt8 | Wire protocol major version. Currently `0x01`. |
| `0x05` | `MsgType` | 2 Bytes | UInt16BE | Message type identifier (Big-Endian). Defines the schema and handler for the payload. |
| `0x07` | `PayloadLength`| 4 Bytes | UInt32BE | Unsigned 32-bit payload length in bytes ($N$). Maximum allowed payload size is $16,777,216$ bytes (16 MiB). |
| `0x0B` | `Payload` | $N$ Bytes | Raw Bytes | The message payload body, serialized deterministically using RFC 8785 (JSON) or CBOR. |
| `0x0B + N` | `Signature` | 64 Bytes | Raw Bytes | Ed25519 signature generated by the sender's DID key over `Header[0..11] || Payload[0..N]`. |

## 4. Cryptographic Standards & Canonicalization

### 4.1 Canonical Serialization (RFC 8785)
All JSON payloads MUST be canonicalized before signature generation and hashing according to **RFC 8785 (JSON Canonicalization Scheme - JCS)**:
- Object keys are sorted lexicographically by Unicode code point.
- Whitespace between tokens is strictly prohibited.
- Floating-point representations must follow ECMAScript canonical numbers.

### 4.2 Ed25519 Signatures (RFC 8032)
- All frame signatures are generated using Ed25519 (Edwards-curve Digital Signature Algorithm).
- Signature Verification Equation:
  $$\text{Verify}(K_{\text{pub}}, \text{SHA256}(\text{Header}_{0..11} \parallel \text{Payload}), \text{Signature}) == \text{True}$$
- Nodes MUST drop packets with invalid signatures and apply a peer reputation penalty score of `-50`.

### 4.3 End-to-End Encryption (E2EE Signal Envelopes)
Signaling payloads (`0x0030` through `0x0033`) are encrypted using **X25519 Diffie-Hellman + ChaCha20-Poly1305 AEAD**:
- Key Derivation:
  $$\text{SharedSecret} = \text{X25519}(K_{\text{priv, sender}}, K_{\text{pub, recipient}})$$
  $$K_{\text{AEAD}} = \text{HKDF-SHA256}(\text{SharedSecret}, \text{salt}=\text{"sovra\_signal\_v1\_salt"}, \text{info}=\text{"signal:"} \parallel \text{DID}_{\text{sender}} \parallel \text{DID}_{\text{recipient}})$$
- 12-byte random cryptographic nonce is prepended to the ciphertext.
- Intermediate relay peers see only the opaque ciphertext and recipient DID.

## 5. Peer Discovery & Transport Independence

A Sovra node discovers peers through four decentralized mechanisms:

1. **Kademlia DHT (BEP 5 compatible):**
   - Nodes maintain a 256-bucket routing table based on XOR distance of Ed25519 DIDs:
     $$d(x, y) = x \oplus y$$
   - `find_node` and `get_providers` RPCs query the $k=20$ closest peers.

2. **Multicast DNS (mDNS) / Local Wi-Fi Discovery:**
   - On LAN or private Wi-Fi subnets, nodes announce service `_sovra-p2p._tcp.local` on multicast address `224.0.0.251:5353`.
   - Direct connection is established via WebRTC-Direct without touching STUN/TURN servers or external WAN routers.

3. **Bluetooth Low Energy (BLE) Mesh:**
   - Mobile and embedded hardware broadcast service UUID `0000SOVR-0000-1000-8000-00805F9B34FB`.
   - Chunk fragmentation adheres to MTU size limits with automatic hop routing (max 7 hops).

4. **GossipSub v1.1 PubSub Mesh:**
   - Topic fanout $D=6$, $D_{\text{low}}=4$, $D_{\text{high}}=12$.
   - Adaptive peer scoring monitors transmission latency and packet validity.

## 6. Sybil Resistance & Anti-Spam (Hashcash PoW)

To prevent mesh flooding without centralized CAPTCHAs:
- Outbound social events (`0x0020`) and call invites (`0x0030`) must contain an 8-byte integer `powNonce`.
- Verification requirement:
  $$\text{LeadingZeros}(\text{SHA256}(\text{EventID} \parallel \text{powNonce})) \ge \text{TargetDifficulty}$$
- Base target difficulty is **16 bits** (~65,536 iterations, ~80ms compute on ARM Cortex-A78 mobile CPU).
- Packets failing PoW are immediately dropped at the ingress buffer before JSON parsing or memory allocation.
