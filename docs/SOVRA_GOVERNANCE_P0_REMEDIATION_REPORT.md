## 2. P0-A: Cryptographic Signer Identity Binding (`MultiPartyApprovalEngine`)

### Identified Vulnerability
Previously, `MultiPartyApprovalEngine.submitApproval` accepted `signerPublicKeyBytes` directly from the caller without verifying that the public key belonged to the asserted `signerDid`. An adversary possessing any Ed25519 key could sign an arbitrary hash, claim the DID of an authorized council member, supply their own public key, and forge valid approvals.

### Remediation Details
- **Location:** `packages/identity/src/governance/multi-party-approval.ts`
- **Key Binding:** Implemented `resolveAuthorizedPublicKey(did, actionType, currentTime)` which queries:
  1. Authoritative external `GovernanceSignerRegistry` (if configured).
  2. Pre-registered `trustedSignerRegistry` (local verified signer enrollments).
  3. Self-authenticating `did:key:z...` derivation (with cryptographic proof).
  4. Revocation and expiration check.
- **Strict Verification:** If the caller provides `signerPublicKeyBytes`, it is strictly verified against the authoritative key:
  ```ts
  if (params.signerPublicKeyBytes) {
    if (bytesToHex(params.signerPublicKeyBytes).toLowerCase() !== bytesToHex(authoritativePubKey).toLowerCase()) {
      throw new ValidationError('Attacker-supplied public key does not match registered signer identity');
    }
  }
  ```
- **Canonical Domain Separation:** Authorization signatures must be signed over a canonical, domain-separated payload generated by `computeCanonicalAuthPayload()`:
  ```ts
  const canonicalString = [
    domain, // 'SOVRA_GOV_AUTH_V1'
    params.chainId,
    params.proposalId,
    params.actionType,
    params.payloadHash,
    params.nonce,
    params.createdAt.toString(),
    params.expiresAt.toString(),
    policyVersion, // '1.0.0'
  ].join(':');
  ```
- **Threshold Enforcement:** Enforces minimum 2-signature multi-party requirement (`requiredApprovals >= 2`).

## 3. P0-B: Authoritative Voter Identity & State Snapshots (`GovernanceVotingEngine`)

### Identified Vulnerability
Previously, `GovernanceVotingEngine.castVote` relied on client-asserted `voterProfile` (stake, account age, usage score) without ledger verification, allowing any actor to forge infinite voting power or bypass the 30-day anti-Sybil maturity gate.

### Remediation Details
- **Location:** `packages/identity/src/governance/voting-engine.ts`
- **Authoritative Provider & Snapshot Store:** Introduced `AuthoritativeVoterDataProvider` and pre-loaded snapshot store (`authoritativeStore` mapping `snapshotId -> did -> { record, pubKey }`).
- **Discrepancy Rejection:** Any caller-submitted `voterProfile` is cross-examined against the authoritative record. Any tampering with stake, account age, or usage score immediately throws:
  ```ts
  if (params.voterProfile.stakeMicroSov !== undefined && params.voterProfile.stakeMicroSov !== resolved.record.stakeMicroSov) {
    throw new ValidationError('Client-asserted voter stake conflicts with authoritative ledger state');
  }
  ```
- **Public Key Binding:** Prevents spoofing of voter keys:
  ```ts
  if (bytesToHex(params.voterPublicKeyBytes).toLowerCase() !== bytesToHex(authoritativePubKey).toLowerCase()) {
    throw new ValidationError('Attacker-supplied voter public key does not match registered voter identity');
  }
  ```
- **Cross-Proposal & Cross-Chain Binding:** Votes are strictly bound via `computeCanonicalVotePayload()` incorporating `domain: 'SOVRA_VOTE_V1'`, `chainId`, `proposalId`, `snapshotId`, `option`, `voterDid`, and `nonce`. Replays across proposals or chains fail signature verification.
- **Fail-Closed Strict Mode:** When `strictAuthoritativeMode` is enabled, unpinned proposals or unregistered voters fail closed.

## 4. P0-C: Admin Endpoint Protection & Unilateral Withdrawal Prohibition

### Identified Vulnerabilities
1. In `scripts/dev-server.ts`, `/api/admin/multisig/propose`, `/api/admin/multisig/sign`, and `/api/admin/circuit-breaker/toggle` fell back to hardcoded mock identities (`did:sovra:admin_alpha` and `treasury_officer_beta`) when authentication headers were missing.
2. In `scripts/admin-security.ts`, constructor seeded a default multi-sig proposal with `did:sovra:admin_alpha`.
3. `/api/admin/treasury/solvency`, `export-csv`, and `stream` lacked RBAC guards.
4. `/api/admin/treasury/withdraw` allowed unilateral treasury withdrawal if a single admin key was presented.

### Remediation Details
- **Location:** `scripts/dev-server.ts`, `scripts/admin-security.ts`, `scripts/routes/admin_features.routes.ts`
- **Elimination of Fallback Identities:** Removed all fallback logic defaulting to `did:sovra:admin_alpha` and `treasury_officer_beta`. Every route strictly authenticates the caller via `checkAdminRbac(req, requiredPerm)` and requires an active session token.
- **Removal of Seed Proposals:** Purged `seedDefaultProposal()` from `SovereignAdminSecurityEngine`. Proposals start empty and must be created by authenticated principals.
- **Constitutional Prohibition on Unilateral Withdrawals:** Replaced the unilateral withdrawal handler at `POST /api/admin/treasury/withdraw` with an absolute prohibition:
  ```ts
  res.writeHead(403, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({
    ok: false,
    error: 'CRITICAL CONSTITUTIONAL VIOLATION: Unilateral treasury withdrawal is strictly prohibited. Multi-party governance authorization required.'
  }));
  ```
- **Treasury Endpoint RBAC:** Hardened `/api/admin/treasury/solvency`, `/api/admin/treasury/export-csv`, and `/api/admin/treasury/stream` with `checkAdminRbac(req, 'treasury:view')`. Unauthenticated calls receive HTTP 401.

## 5. P1-A & P1-B: Anti-Replay Protection & Durable State Hydration

### P1-A Nonce & Timelock Protection
- `MultiPartyApprovalEngine` maintains an immutable `consumedNonces = new Set<string>()`.
- Each action proposal generates a cryptographically random 16-byte hex nonce upon creation.
- At execution time (`executeAction`), the engine verifies:
  1. Action has not expired (`now <= action.expiresAt`).
  2. Timelock delay has elapsed (`now >= action.readyAt + timelockDurationSeconds`).
  3. Action nonce has not been consumed (`!this.consumedNonces.has(action.nonce)`).
- Upon successful execution, `this.consumedNonces.add(action.nonce)` is atomically committed. Re-execution attempts are immediately rejected.

### P1-B State Hydration & Persistence
- Both `MultiPartyApprovalEngine` and `GovernanceVotingEngine` implement comprehensive `exportState()` and `hydrateState()` methods.
- Serialized snapshots capture:
  - Active and executed action proposals with timestamps and approval signatures.
  - Consumed nonce sets.
  - Trusted signer registries with roles, expiration, and revocation status.
  - Cast voter ballots, option weights, and tallies.
  - Pinned snapshot data and authoritative voter eligibility records.
- Enables safe persistence across dev-server and node restarts without data loss or replay vulnerability.
