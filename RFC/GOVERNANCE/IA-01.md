# SOVRA Integration Amendment — IA-01
## Reconciliation of Existing Implementation with Frozen Architecture v1.0

**Status:** Proposed Mandatory Integration Amendment (`IA-01`)  
**Target Baseline:** Frozen Sovra Master Architecture v1.0  
**Acceptance Rule (Section 12):** Becomes binding part of baseline following technical review, regression verification, and community protocol approval.

---

## 1. Architecture Reconciliation (`SOVRA-EXT-CONSENSUS`)
- Go L1 blockchain (`chain/`), `100M` token issuance (`x/issuance`), validator staking, and wallet ledgers are isolated as optional extension **`SOVRA-EXT-CONSENSUS`** ([SOVRA-EXT-CONSENSUS.md](file:///d:/Sovra/RFC/EXTENSIONS/SOVRA-EXT-CONSENSUS.md)).
- Core packages (`@sovra/p2p`, `@sovra/crypto`, `@sovra/protocol`, `@sovra/social`, `@sovra/storage`, `@sovra/messaging`, `@sovra/identity`, `nodes/storage-node`, `apps/sovra-mobile`, `apps/sovra-app`) require ZERO blockchain, token ownership, mining, validator, or transaction-fee dependency for identity, networking, storage, social, or messaging.

## 2. Four Separate Identifiers (`SOVRA-ID` & `SOVRA-NET`)
| Identifier | Format / Encoding | Scope | Lifecycle |
|---|---|---|---|
| **1. Sovra Identity ID** | Bech32m `sovra1...` (`0x01 || SHA-256("SOVRA-ID-v1" || Ed25519Pub)`) | Stable user root identity | Created via CSPRNG key; rotated via epoch chain; backed up encrypted (`scrypt` + AEAD) |
| **2. Device ID** | Signed device authorization record (`device_id` + `device_public_key`) | Individual authorized client device | Delegated by Identity ID; independently revocable without losing root identity |
| **3. Peer ID** | `12D3KooW...` libp2p Ed25519 transport peer key | Network transport node identity | Bound to user/device via `SovraPeerIdentityBinding` (signed off-chain proof) |
| **4. Encryption Key ID** | Bech32m `sovraenc1...` (`0x01 || SHA-256("SOVRA-ENC-ID-v1" || X25519Pub)`) | End-to-end encryption public key reference | Cryptographically separate from signing key; independently rotatable |

**BIP-39 Rule:** BIP-39 (`packages/crypto/src/bip39.ts`, `apps/sovra-mobile/src/services/mnemonic.ts`) is strictly an optional recovery phrase format and NOT an automatic substitute for secure CSPRNG Ed25519 key generation & derivation. All 8 formal test vectors reside in [SOVRA-ID-v1.md](file:///d:/Sovra/RFC/IDENTITY/SOVRA-ID-v1.md).

## 3. Networking (`SOVRA-NET`), Storage (`SOVRA-STORE`) & Sync (`SOVRA-SYNC`) Amendments
- **SOVRA-NET:** Integrates signed peer records, signed QR URIs, LAN UDP mDNS, `/sovra/pex/1.0.0` PEX, IPv4/IPv6, Circuit Relay v2 forwarding, and multi-relay replacement. **STUN never guarantees NAT traversal.**
- **SOVRA-STORE:** Integrates BitSwap DAG replication, `SignedStorageReceipt`, PoR remote challenges, `RetentionPolicy`, expired provider pruning, replica repair, and multi-operator failure-domain checks. **PoR proves retrieval at challenge time under the challenge model, not future availability.**
- **SOVRA-DATA:** All 17 `SOVRA-EVT` event types enforce versioned payload schemas; CRDTs apply only where documented convergence rules hold; financial/inventory/order transitions use transactional state machines.

## 4. Optional Incentives (`Section 7`) & Signed Updates (`Section 8`)
- Seeder/relay receipts require downloader co-signatures, unique `receiptId`s, replay defense, self-report rejection, and wash-trading detection via a decoupled `OptionalSettlementAdapter` (`NoopNonTokenSettlementAdapter` default).
- M-of-N software updates require threshold signer quorum, compromised key revocation & quorum signer rotation (`SignedSignerRotationNotice`), downgrade checks, reproducible-build digest provenance, and independent multi-operator mirrors (`mirrors[]`) with zero founder-only signing key.

## 5. Honest Certification & P0 Closure Rule (`Sections 9 & 10`)
- Existing lab/local multi-node results are **implementation evidence**, NOT multi-organization real-world certification.
- **Zero P0 issue may be closed solely because a simulation or localhost test passed.** Real-world multi-org (`>= 3` independent organizations across geographically separated ISP networks) and physical public WAN / mobile RF tests remain explicitly tracked in [IA-01_ACCEPTANCE_REPORT.md](file:///d:/Sovra/RFC/GOVERNANCE/IA-01_ACCEPTANCE_REPORT.md).
